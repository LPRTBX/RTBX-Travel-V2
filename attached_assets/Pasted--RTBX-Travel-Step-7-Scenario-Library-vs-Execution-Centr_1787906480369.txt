# 1. Objective

Establish three clear responsibilities:

## Travel Scenarios

**Scenario Library / Explorer**

Used to understand:

* the moment
* trigger
* signals
* governance
* accountable role
* linked playbook
* communications
* escalation
* evidence
* outcomes
* maturity

It explains how the scenario is designed.

## Build & Configure

**Activation and configuration**

Used to select:

* operating systems
* scenario
* signal mode
* roles
* governance settings
* playbook configuration
* communications
* evidence
* outcome targets

It determines how a scenario will operate in a specific deployment.

## Execution Centre

**Canonical runtime**

Used to:

* receive/trigger a signal
* understand context
* apply governance
* route decision
* activate the playbook
* progress actions
* approve communications
* escalate
* capture evidence
* record outcomes
* close the execution
* review learning

The same scenario should not have independent competing runtime logic elsewhere.

# 6. Deep-link strategy

Current hash-style links such as:

```text id="b95dv8"
/partner-room/travel-scenarios#<scenario-id>
```

must reliably select and focus the intended scenario.

Choose one canonical strategy.

## Preferred

Use route-based scenario detail:

```text id="70or5c"
/partner-room/travel-scenarios/:scenarioId
```

Examples:

```text id="g5ph3g"
/partner-room/travel-scenarios/repeat-guest-room-not-ready
/partner-room/travel-scenarios/service-backlog
/partner-room/travel-scenarios/maintenance-defect
```

The base:

```text id="vo9u4f"
/partner-room/travel-scenarios
```

remains the library/index.

## Acceptable alternative

If route-based detail is too disruptive, retain hashes but ensure:

* every scenario has a matching DOM ID
* hash changes select the scenario
* page loads with that scenario open
* page scrolls/focuses appropriately
* browser Back/Forward works

Do not keep non-functional hashes.

# 11. Remove duplicated runtime logic

Audit:

* Travel Scenarios
* Demo Paths
* Live/Interactive Demos
* Validation Replay
* Operator Demo
* Guest Demo
* Dual View
* Execution Centre

Classify each as:

## Explorer

Static/interactive explanation.

## Role View

Shows one perspective of a scenario.

## Replay

Demonstrates a predetermined trace.

## Runtime

Actually progresses canonical execution state.

Only the Execution Centre should be the canonical runtime.

Other surfaces may simulate or replay, but must not maintain competing production-like state machines.
