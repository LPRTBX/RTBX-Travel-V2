## Sprint 2 — Shared RTBX Core Alignment

You are working on the existing **RTBX Travel Partner Room V2** application.

Sprint 1 should already have:

* Confirmed the canonical application
* Stabilised the repository
* Archived or isolated legacy WELBX source

---

# 1. Sprint objective

Align RTBX Travel with the shared RTBX Main platform so that the Travel site clearly communicates:

1. What belongs to the shared RTBX Core
2. What is configured specifically for Travel
3. What becomes a Travel operating system
4. What is configured for an individual property or customer
5. What is working proof, simulation, planned or production engineering

The Travel site must no longer appear to contain a separate intelligence architecture that competes with or redefines RTBX Main.

The central principle is:

> RTBX Travel configures the shared RTBX Intelligence Engine for travel environments. It does not redefine the RTBX platform.

# 3. Canonical RTBX architecture

The Travel application must use the following shared RTBX architecture consistently.

## RTBX Intelligence Engine

The shared engine is:

> **Connect → Understand → Decide → Act → Learn**

This sequence must become the primary operating logic across Travel.

### Connect

Connect existing systems, sources, people, roles and channels.

Travel examples include:

* Property management systems
* Housekeeping systems
* Task and workforce systems
* Maintenance systems
* CRM and loyalty platforms
* Guest applications
* Messaging platforms
* Booking and reservation sources
* Policies and operating procedures
* Role and identity information
* External transport or disruption data
* Partner platforms
* Manual staff signals
* Guest-submitted signals

### Understand

Interpret signals in context and determine whether an important Travel moment exists.

Travel examples include:

* Guest state
* Arrival state
* Room-readiness risk
* Service delay
* Repeated requests
* Maintenance impact
* Guest distress
* Welfare concern
* Operational pressure
* Loyalty context
* Recovery opportunity
* Escalation risk
* Pattern recognition

### Decide

Apply the correct governance, policy, threshold, permission and accountability.

Travel examples include:

* Brand standards
* Property procedures
* Safety rules
* Welfare requirements
* Service-level thresholds
* Approval requirements
* Escalation rules
* Role permissions
* Communications controls
* Evidence requirements
* Customer-specific decision rules

### Act

Coordinate the response through the appropriate people, playbooks, prompts, communications and systems.

Travel examples include:

* Playbook activation
* Role routing
* Staff prompts
* Guest communications
* Task creation
* Escalation
* Approval
* Recovery action
* Operational handoff
* Evidence capture
* Central Comms OS
* Execution Centre

### Learn

Record what happened, measure outcomes and improve future decisions and playbooks.

Travel examples include:

* Evidence Ledger
* Outcome Ledger
* Service performance
* Response time
* Resolution quality
* Escalation performance
* Repeat issue detection
* Guest outcome
* Staff adoption
* Operational learning
* Cross-property patterns
* Playbook refinement
* Value measurement

# 13. Proof maturity standard

Apply the Sprint 1 proof-boundary standard consistently to major architecture and proof pages.

## Working Proof

A functioning interactive interface demonstrating the intended workflow.

## Prototype

A partial capability or configurable interface not yet connected to the full runtime.

## Simulation

A workflow using synthetic signals, actions, messages, evidence or outcomes.

## Connector-ready

Only where an interface contract, field mapping and test harness exist.

## Integrated

Only where data has been successfully exchanged with a named external system.

## Production

Only where the capability is deployed with:

* Production authentication
* Monitoring
* Data controls
* Reliability controls
* Operational support
* Customer-approved governance

Do not use maturity labels decoratively.
