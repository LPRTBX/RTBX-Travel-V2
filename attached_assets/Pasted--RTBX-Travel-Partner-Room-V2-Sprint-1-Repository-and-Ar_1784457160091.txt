# RTBX Travel Partner Room V2

## Sprint 1 — Repository and Architecture Stabilisation

You are working on the existing **RTBX Travel Partner Room V2** application.

This is an already substantial and commercially valuable product. **Do not rebuild it. Do not redesign the product. Do not add new operating systems, scenarios, pages, demonstrations or commercial concepts.**

The purpose of this sprint is to stabilise the repository, remove legacy confusion, establish canonical routes and ensure the current application can be reliably maintained, tested and deployed.

---

# 1. Sprint objective

Create one clean, identifiable and technically stable RTBX Travel application by:

1. Confirming the canonical application entry point
2. Protecting the existing Travel Partner Room
3. Archiving obsolete WELBX source files
4. Removing stale branding from the active application
5. Establishing one canonical route for each product concept
6. Resolving broken or misleading content-loading behaviour
7. Pinning the runtime and package manager
8. Adding baseline route, link and build verification
9. Documenting what remains active, redirected, archived and deferred

This is a stabilisation sprint only.

# 6. Establish a canonical route register

Create:

```text
docs/route-register.md
```

The register must include:

| Field                    | Description                            |
| ------------------------ | -------------------------------------- |
| Canonical route          | The approved primary route             |
| Page/component           | Component rendered                     |
| Page purpose             | What the route is for                  |
| Status                   | Active, redirect, archived or deferred |
| Alias routes             | Existing alternate paths               |
| Navigation location      | Where it appears                       |
| External dependency risk | Whether old links may exist            |
| Action                   | Keep, redirect, merge later or archive |

## Route rules

* Every distinct product concept must have one canonical route.
* Duplicate route names should redirect to the canonical route.
* Existing public links must not be broken unnecessarily.
* Redirects must be deliberate and documented.
* No alias route should independently render a separate duplicate page.
* No route should rely on the wildcard application fallback when an explicit route is appropriate.
* The root `/` route must intentionally redirect to or render the correct Travel entry point.
* Any stale `/` links in Story Lab or other pages must be corrected.
* Temporary compatibility redirects must be clearly marked.

# 7. Correct content-loading integrity

The application currently attempts to load:

```text
/partner-content.json
```

Determine whether this file is intended to be:

* A deployed public content file
* A generated build artifact
* A local override
* A future CMS mechanism
* An obsolete feature

## Required resolution

Choose one deliberate solution.

### Option A — Activate it properly

If the editable-content mechanism is genuinely required:

* Add the file to the correct public asset directory
* Define and validate its schema
* Add safe fallback handling
* Add a visible development warning when loading fails
* Prevent malformed content from breaking the app
* Document which fields can be overridden
* Add a test verifying that the content file loads

### Option B — Remove the false mechanism

If no external content file is currently used:

* Remove the unsuccessful fetch
* Keep the current internal content source
* Remove silent network failure behaviour
* Document that content is currently code-managed
* Record external content management as deferred

Do not leave a silent request for a missing file.

# 8. Runtime and package management

The repository must produce consistent results across:

* Local development
* Replit or equivalent development environment
* GitHub Actions
* Production build environment

## Required actions

1. Confirm whether the workspace uses pnpm, npm or another package manager.
2. Use only one package manager for the canonical workflow.

```json

```

```text

```

5. Ensure the selected pnpm version is compatible with the selected Node version.
6. Remove conflicting lockfiles only after confirming the canonical package manager.
7. Ensure CI uses the same Node and package-manager versions.
8. Ensure workspace install commands operate from the correct directory.
9. Document the commands in the root README.

Do not upgrade dependencies broadly unless required to make the current application install or build.

# 10. Baseline automated verification

Add lightweight tests and scripts appropriate to the existing stack.

## Minimum required checks

### Route smoke test

Verify that every canonical route:

* Resolves
* Renders without crashing
* Does not fall into the not-found page
* Does not produce an unhandled runtime exception

### Internal-link test

* Match a canonical route or documented redirect
* Do not point to archived pages
* Do not point to stale root paths
* Do not use broken relative links

### Missing asset check

* JSON files

* Fonts

### Build and typecheck

* Dependency installation
* Typecheck
