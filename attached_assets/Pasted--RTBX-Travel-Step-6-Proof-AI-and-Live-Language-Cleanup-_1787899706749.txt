# 2. Approved proof taxonomy

Use only these maturity categories:

## Working Proof

A functioning interactive interface or workflow that demonstrates intended behaviour.

## Prototype

A partial capability or configuration experience not yet connected to full production infrastructure.

## Simulation

A workflow using synthetic signals, decisions, messages, actions, evidence or outcomes.

## Connector-ready

Only where all of the following exist:

* interface contract
* field mapping
* authentication approach
* test harness
* error-handling definition

## Integrated

Only where data has been successfully exchanged with a named external system.

## Production

Only where the capability is deployed with:

* production authentication
* monitoring
* data controls
* reliability controls
* customer-approved governance
* operational support

## Planned

Architecturally defined but not yet implemented or validated.

Do not introduce alternative maturity categories without explicit reason.

# 5. “Live” language rules

The word **live** may only be used where it is literally true.

Acceptable examples:

* “The Partner Room is live at this URL.”
* “The deployed demonstration is available.”
* “A live customer pilot is currently operating” — only if verified.
* “Live integration with [named system]” — only if verified.

Do not use “live” to mean:

* interactive
* clickable
* simulated
* rendered
* demonstrable
* configured
* prototype

Replace phrases such as:

### “Live MVP”

with:

> **Deployed MVP Preview**

or:

> **Working MVP Preview**

### “Live Demo”

with:

> **Interactive Demo**

or:

> **Working Product Demo**

### “Run Live Scenario”

with:

> **Run Scenario**

or:

> **Run Interactive Scenario**

### “Live Signals”

with:

> **Simulated Signals**

or:

> **Configured Signal Sources**

depending on actual maturity.

### “Live RTBX Core signal sources”

with:

> **Demonstrated RTBX signal sources**

or:

> **Configured signal sources**

unless they are genuinely integrated.

# 6. “Real-time” language rules

Use **real-time** only where the current system actually processes real events in real time.

If the current proof uses synthetic or manually triggered events, use alternatives such as:

* event-driven
* near-real-time capable
* designed for real-time operation
* responsive operational workflow
* triggered by incoming signals
* simulated event flow

Example:

### Avoid

> RTBX is a real-time execution layer.

### Prefer

> RTBX is designed as an event-driven intelligence and execution layer that can operate on approved real-time signals when connected.

For current proof:

> The demonstration uses synthetic signals to show how RTBX would respond to operational events.

* threshold-based
* configuration-driven

Do not use generic:

where the underlying workflow is not actually invoking AI.

# 8. AI action taxonomy

Where AI appears in UI or copy, classify its role as one of:

## Draft

AI prepares text for human review.

## Recommend

AI proposes a possible action.

## Classify

AI assists with categorisation or context.

## Summarise

AI condenses information.

## Detect pattern

AI identifies a potential pattern or anomaly.

## Automate rule-based action

This is not necessarily AI.

If the action is deterministic, label it as:

> automated rule-based action

not:

> AI action

## Human decision

Human owns the decision.

Do not blur these categories.
